# Задание B: Анализ ошибок в CI/CD конфигурации

## Найденные проблемы

### 1. Пароль в открытом виде в переменных
**Что не так:** В переменных прописан пароль от БД в открытом виде: `DB_PASSWORD: "prod_pa$$w0rd_2024"`.

**Последствия:** Пароль попадает в git историю и виден всем, у кого есть доступ к репозиторию. Это критическая уязвимость безопасности.

**Как исправить:** Использовать защищенные переменные GitLab (Settings → CI/CD → Variables) с флагами Masked и Protected. В коде оставить только ссылку: `DB_PASSWORD: $DB_PASSWORD`.

### 2. Неправильный порядок стадий
**Что не так:** Стадия `lint` указана после `build`, хотя должна быть первой: `stages: [test, build, lint, deploy]`.

**Последствия:** Сначала запускаются тесты и сборка, и только потом линтер. Это замедляет обнаружение простых ошибок стиля кода. Линтер должен быть самым первым и быстрым этапом.

**Как исправить:** Изменить порядок на: `stages: [lint, test, build, deploy]`.

### 3. Игнорирование ошибок линтера
**Что не так:** У джоба `lint` стоит `allow_failure: true`.

**Последствия:** Pipeline будет считаться успешным, даже если код не соответствует стандартам. Это приводит к захламлению кодовой базы.

**Как исправить:** Убрать `allow_failure: true` или оставить его только для некритичных проверок.

### 4. Игнорирование падения тестов
**Что не так:** В джобе `test` команда `pytest tests/ || true` всегда завершается успешно даже при падении тестов.

**Последствия:** Pipeline показывает зеленый статус, хотя тесты падают. Баги попадают в продакшн. Это самая опасная ошибка после утечки пароля.

**Как исправить:** Убрать `|| true`, чтобы джоб падал при ошибках в тестах.

### 5. Отсутствие кеширования зависимостей
**Что не так:** В джобах `lint` и `test` каждый раз заново устанавливаются зависимости без кеширования.

**Последствия:** Pipeline работает 12 минут вместо 3 из-за постоянной переустановки пакетов.

**Как исправить:** Добавить кеширование:
```yaml
cache:
  key: $CI_COMMIT_REF_SLUG
  paths:
    - .cache/pip
```

### 6. Использование тега `latest` для образов
**Что не так:** В джобах используются образы с тегом `latest`: `image: python:latest`, `image: docker:latest`.

**Последствия:** Нестабильная среда сборки - образ может измениться между запусками, что приведет к непредсказуемым результатам и сложностям в отладке.

**Как исправить:** Указать конкретные версии: `image: python:3.11-slim`, `image: docker:24-dind`.

### 7. Отсутствие Docker-in-Docker сервиса
**Что не так:** Джоб `build` использует команды docker, но не настроен Docker-in-Docker сервис.

**Последствия:** Сборка образа будет падать с ошибкой "Cannot connect to Docker daemon".

**Как исправить:** Добавить в джоб `build`:
```yaml
services:
  - docker:24-dind
variables:
  DOCKER_HOST: tcp://docker:2375
```

### 8. Deploy срабатывает на всех ветках
**Что не так:** В джобе `deploy` указано `only: branches`, что означает запуск на любой ветке.

**Последствия:** Деплой на продакшн происходит из любой ветки, включая feature-ветки. Это может привести к деплою недоработанного или непротестированного кода.

**Как исправить:** Изменить на `only: [main]` или использовать `rules` с условием на main ветку.

### 9. Отсутствие зависимостей между стадиями
**Что не так:** Не указаны зависимости через `needs`, все джобы запускаются последовательно по стадиям.

**Последствия:** Параллельные джобы (`lint` и `test`) не могут выполняться одновременно, что увеличивает общее время pipeline.

**Как исправить:** Добавить `needs: []` для `lint` и `test`, чтобы они запускались параллельно.

### 10. Небезопасное SSH подключение
**Что не так:** Опция `-o StrictHostKeyChecking=no` в команде SSH отключает проверку ключа хоста.

**Последствия:** Уязвимость к MITM-атакам. Плюс подключение под root - нарушение принципа минимальных привилегий.

**Как исправить:** Добавить SSH ключ сервера в known_hosts и использовать непривилегированного пользователя для деплоя.

## Цепочка ошибок и инцидент

**Сценарий инцидента:**

Разработчик создает feature-ветку для новой функции. Пишет код с ошибками стиля и падающими тестами. Пушит в репозиторий.

Pipeline запускается: `test` с `|| true` показывает зеленый статус, `lint` с `allow_failure: true` тоже зеленый. Джоб `build` выполняется долго из-за отсутствия кеша. Затем `deploy` с `only: branches` деплоит сломанный код на продакшн.

В результате на продакшн попал нерабочий код с утекшим паролем от БД, который был в истории репозитория. Инцидент обнаружен только после жалоб пользователей.
